# Story 3.2.1: Execute Endpoint Error Response Specification

**Priority:** High  
**Dependencies:** Story 3.2 (Error Handling)  
**Status:** ⏳ Not Started

---

## Problem Statement

Currently, the `/execute` endpoint fails silently when errors occur. Clients cannot determine:
- Whether a request succeeded or failed
- Why a request failed (specific error reason)
- What corrective action to take

The client needs explicit, structured error responses with appropriate HTTP status codes.

---

## Description

Implement standardized error response format for the `/execute` endpoint that clearly communicates failure reasons and HTTP status codes to clients.

---

## Error Scenarios & HTTP Status Codes

| Scenario | HTTP Code | Client Knows | Example |
|----------|-----------|--------------|---------|
| Missing/invalid API key | **401** | Authentication failed | `"error": "Unauthorized: Invalid or missing API key"` |
| Invalid request body | **400** | Bad request format | `"error": "Bad Request: Invalid JSON or missing 'code' field"` |
| Unsupported language | **400** | Language not supported | `"error": "Bad Request: Language 'rust' not supported"` |
| Endpoint not found | **404** | Endpoint doesn't exist | `"error": "Not Found: /invalid-endpoint"` |
| Syntax error in code | **400** | Code has syntax issues | `"error": "Syntax Error: Line 5, invalid syntax..."` |
| Runtime error (execution failed) | **200** | Execution ran, test failed | `"execution_error": "RuntimeError: division by zero at line 3"` |
| Timeout (code took too long) | **500** | Code timeout | `"error": "Internal Server Error: Execution timed out after 5s"` |
| Docker/container failure | **500** | Container system error | `"error": "Internal Server Error: Container failed to start"` |
| Server error | **500** | Server issue | `"error": "Internal Server Error: {details}"` |

---

## Response Format Specification

### Success Response (200)
```json
{
  "status": "success",
  "language": "python",
  "execution_time_ms": 1234,
  "results": {
    "passed": 3,
    "failed": 0,
    "output": "..."
  }
}
```

### Client Error (400/401/404)
```json
{
  "status": "error",
  "code": "INVALID_REQUEST",
  "error": "Bad Request: Invalid JSON or missing 'code' field",
  "details": {
    "field": "code",
    "reason": "Required field missing"
  }
}
```

### Server Error (5xx)
```json
{
  "status": "error",
  "code": "INTERNAL_ERROR",
  "error": "Internal Server Error: Container failed to start",
  "details": {
    "container_error": "Container exited with code 137"
  }
}
```

### Execution Error (200 with execution failure)
```json
{
  "status": "success",
  "language": "python",
  "execution_time_ms": 500,
  "execution_error": "SyntaxError: invalid syntax at line 5",
  "results": {
    "passed": 0,
    "failed": 1,
    "output": "..."
  }
}
```

- [ ] Implement 400 (Bad Request) for invalid request body

- [x] Error response includes `status`, `code`, `error`, and `details` fields
- [x] Client can distinguish between auth, validation, and server errors
- [x] Execution errors are separate from request errors (200 + execution_error)
- [x] Error messages are user-friendly and actionable
- [x] All errors are logged with request ID

## Testing Plan

1. **401 Unauthorized**
   - Request without API key → expect 401 + error message
   - Request with invalid key → expect 401 + error message

2. **400 Bad Request**
   - Malformed JSON → expect 400 + field error
   - Missing `code` field → expect 400 + missing field error
   - Unsupported language → expect 400 + language error

3. **404 Not Found**
   - Request to `/invalid-endpoint` → expect 404 + not found message

4. **Execution Errors (200 OK)**
   - Syntax error in code → expect 200 + `execution_error` field
   - Runtime error → expect 200 + `execution_error` field
   - Timeout → expect 500 + timeout message

5. **500 Server Error**
   - Docker container failure → expect 500 + container error details
